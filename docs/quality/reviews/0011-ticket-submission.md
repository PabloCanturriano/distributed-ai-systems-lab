# Atomic ticket submission

Status: prepared for exact-patch review, not committed or pushed. Base: `0d6e59e`. The previous client-evaluation and CI patches were approved and committed. This implements the first internal submission transaction from the accepted contracts/data model, not an HTTP endpoint or complete ticket workflow.

## Change and scope

Proposed commit: `feat: persist ticket submissions and outbox events atomically`.

- `apps/api/src/ticket-submission.ts`: validates input, rechecks active principal membership/create permission, reserves a tenant/operation/collection/key identity, and commits ticket, queued execution, immutable receipt and pending outbox event together. A matching retry returns the original receipt; changed input returns a safe conflict. No SQL, payload or private error is logged or copied into errors.
- `database/migrations/1795046400000_ticket-submission.cjs`: four tables, tenant-consistent relationships and deferred integrity for current execution, key reservation and scheduling event. API receives SELECT and specified INSERT columns only; it cannot rewrite receipts/event bytes, delete rows or set publication state. Worker/relay grants, publication claims and execution transitions remain later work. Historical migrations are unchanged; destructive down migration is refused.
- `apps/api/package.json`, `package-lock.json`: declares the already resolved Zod 4.6.7 directly in API. No existing version is upgraded.
- `tests/database/ticket-submission.test.cjs`: 31 real PostgreSQL cases. `tests/database/foundation.test.cjs` updates expected schema/history and verifies upgrades from both seeded two- and three-migration baselines. Root `package.json` builds the API as well as database before the database suites, including in a clean CI job.
- Root/documentation-map/roadmap status, the data-model status and this report are updated; no new design proposal or runtime service is added.

The module accepts server-resolved tenant/principal context only. It has no route or caller-facing tenant selection. Bearer authentication, credential revocation checks, ingress/principal limits and HTTP error mapping must precede a public route; this permission recheck is not a substitute. A caller-owned pool supplies connection acquisition and client-side query deadlines; each transaction uses one client, explicit READ COMMITTED isolation, 2-second lock/5-second statement bounds and a 10-second idle-transaction bound.

Uniqueness is reserved before business inserts. A separate statement reads the concurrent winner after `ON CONFLICT DO NOTHING`, consistent with [PostgreSQL READ COMMITTED behavior](https://www.postgresql.org/docs/17/transaction-iso.html). Deferred foreign keys forbid committing a reservation without its execution, or an execution without its scheduling event. All statements share a checked-out client as required by [node-postgres](https://node-postgres.com/features/transactions).

Messages use trim, code-point bounds, exact interior whitespace/case and no Unicode normalization. The internal validator rejects NUL and unpaired surrogates because they cannot round-trip as PostgreSQL UTF-8 text; corresponding HTTP validation must retain that explicit restriction. Hash input is version-scoped UTF-8 JSON. Outbox payload is immutable JSON text with a SHA-256 digest of those exact bytes, avoiding digest changes from JSONB key reordering. The event excludes ticket message text. Execution corpus/profile references will be added when retrieval is introduced, as specified by the AI design; none are fabricated here.

## Actual verification on 2026-11-19

Red: with the existing database initialized successfully, the first submission test failed because the submission module was absent. After implementation:

- `npm run test:database`: **60 tests passed** in two suites (31 submission cases and 29 foundation cases). Eight concurrent identical requests are coordinated with a test-only advisory-lock trigger; observed transaction-ID lock contention confirms overlapping reservations. All return one receipt with one set of rows. Concurrent changed input produces one winner and one conflict.
- Rollback is verified after each of the four INSERT stages using database-only failure triggers. A rolled-back competing reservation releases its key; unresolved contention returns a safe bounded failure, and a later retry succeeds. A test simulates losing the client acknowledgement after a real COMMIT: rows remain committed and retry returns the stored receipt. This is a controlled transport-error seam, not proof of every possible network failure.
- Validation, Unicode/code-point limits, trim equivalence, case/interior-space conflicts, case-sensitive keys, tenant scopes, reader/disabled/wrong-tenant principal checks and stable receipts after a migrator-only lifecycle mutation pass. Constraint/privilege tests independently reject cross-tenant references, incomplete commits, missing outbox metadata, event/receipt rewrites and forged publication state.
- Both prior seeded migration baselines upgrade with credentials and unrelated data preserved. Repeat migration is a no-op. `npm run check` passed formatting, workspace type checks/builds and **52 fast tests**. `npm run test:containers` passed both application-image builds and lifecycle/restriction checks.

`npm run test:compose` also passed initialization, dependency stop/pause recovery, clean shutdown, persistence, safe logs and missing-credential failure gates with the new migration. Final formatting, relative links and whitespace passed. Current npm audit reports 24 moderate affected entries in the full tool graph and 0 findings for API/worker production dependencies; OS/image scanning was not performed. SQL server timeouts alone do not establish complete network-operation deadlines; future HTTP wiring must use bounded pool/client settings. Native Kafka compatibility is not rerun: this patch adds no Kafka client or broker configuration. No business HTTP/EVENT acceptance family is marked complete; these are persistence-level portions of submission/idempotency, DATA-01/DATA-02 and role-scope evidence. No publisher, consumer, inbox/job, result, replay, authentication, limiter or CLI is wired by this patch.
