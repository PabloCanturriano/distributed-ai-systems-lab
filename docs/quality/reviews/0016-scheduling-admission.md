# Atomic scheduling admission

Status: prepared for exact-patch review under the accepted SQL handoff architecture in ADR-0001/0002. Not committed or pushed. Base `4723309` contains the approved real publisher. Proposed commit: `feat: add atomic inbox and scheduling admission`.

## Purpose and affected files

This slice implements the PostgreSQL boundary that a future Kafka callback calls before acknowledging a delivery. Identical redelivery retains one inbox identity; different valid event IDs for one execution retain their identities but create at most one job. Invalid or contradictory input creates durable metadata-only quarantine. No application consumer, offset coordinator, executor or public route is activated.

- `database/migrations/1795219200000_scheduling-admission.cjs`: inbox uniqueness per consumer/event, jobs unique per ticket/generation, tenant-consistent execution/source-inbox FKs, immutable admission ledgers, and quarantine unique per consumer/topic/partition/offset. Offsets use PostgreSQL bigint. No data backfill bypasses Kafka, no existing row is rewritten, and destructive rollback is refused.
- Jobs are deliberately queued-only admission records with zero attempts and the reviewed default budget of three. They cannot run until a later executor migration adds ownership/attempt states. The worker INSERT grant cannot override status, availability or budgets. Existing jobs remain authoritative after an execution becomes terminal.
- Worker privileges permit authoritative metadata reads and admission INSERTs, without ticket-message/credential reads, pointer changes or ledger updates/deletes. PostgreSQL requires UPDATE permission on a column for ticket row locking: the grant covers only `tickets.id`, whose existing execution FKs prevent identity changes. The real non-admin login tests this constraint and the denied pointer/content operations. No security-definer routine or new role/login is introduced.
- `apps/worker/src/scheduling-event.ts`: Zod boundary validation, 16 KiB UTF-8 input limit, strict decoding, supported type/version, UUIDs/timestamps/generation/reason and ticket-key agreement. Additive fields do not influence admission. Source identity is validated separately; exact signed-64-bit offset strings do not pass through JavaScript Number. Invalid source metadata raises a safe error because no trustworthy quarantine position can be invented.
- `apps/worker/src/scheduling-admissions.ts`: one checked-out client/transaction with `lab_worker` and finite SQL bounds. Lock the authoritative ticket before deciding generation/reason, atomically insert inbox and job, or retain quarantine/digest/safe reason. Same event ID with changed bytes is quarantined. Old generations are stale; future/unknown/mismatched executions cannot schedule. Reusing an already quarantined source position cannot silently replace its content with runnable work.
- The method resolves only after COMMIT. Connection, SQL or ambiguous commit failure rejects with `DEPENDENCY_UNAVAILABLE` and discards the uncertain connection. Its caller must supply a bounded pool and must not acknowledge a rejected admission. This is not yet proof of actual broker offset handling.
- `apps/worker/package.json`, `package-lock.json`: declare the already resolved Zod **4.6.7** directly, installed offline with lifecycle hooks disabled. No package version or integrity changes.
- `tests/scheduling-event.test.cjs`, `tests/database/ticket-submission.test.cjs`, `tests/database/foundation.test.cjs`: event validation, real admission/locking/rollback/collision/privilege cases and six-migration history/upgrade paths. Existing fixture cleanup explicitly includes the new FK-related tables.
- Short status updates in README/map/roadmap/contracts/data model and relay evidence. [ADR-0007](../../adr/0007-local-scheduling-consumer.md) proposes the separate native-consumer adoption decision; it is not implemented by this patch.

## Actual verification on 2026-11-20

Red: after PostgreSQL bootstrap succeeded, the first admission test failed because `scheduling-admissions.js` did not exist. After implementation:

- `npm run check`: formatting, type checks/builds and **110 fast tests in 9 suites** passed. Event cases include invalid UTF-8, tombstones, oversize data, malformed UUID/date/generation/reason, unsupported versions/types, mismatched keys, additive-field isolation and invalid source offsets rejected before SQL.
- `npm run test:database`: **113 real PostgreSQL tests in 2 suites** passed, including the existing API/outbox scenarios. Tests use an authenticated NOINHERIT worker login selecting only `lab_worker`, not a superuser masquerading as the runtime role.
- Eight concurrent identical deliveries yield one scheduled identity/job and seven duplicates. Eight distinct event IDs for one generation yield eight inbox rows and one job. Concurrent ID reuse across two valid tickets schedules only one and quarantines the collision. Changed bytes under an admitted ID are quarantined; retry preserves the original record/digest.
- Job INSERT failure rolls back the inbox too; quarantine INSERT failure cannot resolve as handled. A real SQL commit followed by a simulated lost client acknowledgement retains the original job; redelivery returns duplicate without replacement. Failure details stay generic.
- A replay fixture holds the ticket lock while admission is proven blocked through pg_stat_activity, then commits generation two. The waiting old event is classified stale with no job. This uses controlled SQL fixtures; it does not implement a replay API or executor. Another event after terminal execution retains the original job; terminal execution without a job is not re-enqueued.
- Cross-tenant source-inbox references fail their FK. Runtime grants deny credentials, ticket messages/pointer changes, raw outbox payload reads, ledger mutation and budget overrides; attempts to rename a referenced ticket fail the existing FK. Quarantine stores no raw payload/key. Offset strings above Number.MAX_SAFE_INTEGER and at signed-64-bit maximum remain exact.
- Seeded two-, three-, four- and five-migration baselines upgrade to six while preserving credentials, unrelated rows and existing pending event bytes/digests/messages. Repeat migration is a no-op.

`npm run test:compose` and `npm run test:relay` passed with the sixth migration: authenticated HTTP/idempotency/rate-limit/read checks, dependency stop/pause recovery, persisted credentials/data, missing-secret gates and real Kafka publication/outage/crash recovery. These regression runs do not activate admission or a consumer. Final formatting, relative documentation links and whitespace checks passed. Environment remains Node **24.22.3**, Docker Desktop **29.2.1**/Linux arm64 and PostgreSQL **17.12**/pgvector **0.8.7**. No new native-client compatibility, hosted CI, OS/native scanning or performance claim is made.

## Remaining boundary

The integration inputs are exact submitted-event fixtures passed directly into admission, not Kafka consumer callbacks. No current test establishes committed broker offsets, rebalance ordering or a complete ticket workflow. The existing real publisher remains available, and tickets remain queued. The next slice requires explicit review of [ADR-0007](../../adr/0007-local-scheduling-consumer.md) because ADR-0006 adopted the native client solely for publication.

The complete implementation patch, including new files, needs owner approval under [AGENTS.md](../../../AGENTS.md) before commit. Consumer architecture approval is separate from this SQL commit and from its future exact implementation patch. Neither authorizes push or release.
