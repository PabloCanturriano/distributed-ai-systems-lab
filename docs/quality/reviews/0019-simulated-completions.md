## Purpose and affected files

This slice closes the durable result-write/read boundary for a minimal simulated abstention. It does not activate an automatic executor or model adapter. A trusted test caller completes a real Kafka-admitted job, then authenticates through the public HTTP GET route to observe the persisted result. Successful persistence is not presented as real-model inference or citation quality.

- `database/migrations/1795392000000_execution-completion.cjs`: immutable results unique per execution/job, with tenant-consistent execution/job FKs and an attempt/job/count FK. Result storage currently permits only `insufficient_evidence` and `provider_mode=simulated`, with a bounded 8 KiB answer. Job/attempt states extend to completed/succeeded. Existing running/expired/retryable/failed history remains valid. No citation table or unconstrained answered result is introduced, and destructive rollback is refused.
- Worker receives result SELECT/column-scoped INSERT, without UPDATE/DELETE. API receives only safe result/job projection columns, excluding attempt tokens, job IDs and internal attempt metadata. Existing privileged initializer/runtime boundaries are retained. No credentials, dependencies or new Compose services are introduced.
- `apps/worker/src/execution-ownership.ts`: `complete(jobId,attemptId,input)` validates a strict two-field simulated-abstention input before SQL. Unsupported outcomes, provider-mode spoofing, citations, empty/oversized/invalid-Unicode answers are rejected without a connection. Ticket -> execution -> job locking and fresh generation/token/lease checks occur in the same transaction as result insertion and all three lifecycle changes. A stale token returns false; an uncertain commit rejects generically and later attempts cannot overwrite the immutable result. Attempt count and provider mode come from trusted server state, not caller summary fields.
- `apps/api/src/ticket-read.ts`: a single tenant/current-generation-scoped join reads coherent lifecycle/result/job state. Completed output includes the stored answer, empty citations/tools, simulated provider mode and actual attempt count. Failed output contains only EXECUTION_FAILED/ATTEMPTS_EXHAUSTED and fixed messages. Unsupported or inconsistent terminal rows remain generic 503 responses; missing/foreign tickets retain the same 404 behavior. Queued/processing responses remain compatible.
- `tests/database/execution-ownership.test.cjs`, `tests/execution-ownership.test.cjs`: result atomicity, failed writes, expired/replaced/generation-stale owners, completion/failure race, lost acknowledgement, immutable results, scoped reads, safe grants, Unicode limits and unsupported-output rejection. `tests/database/ticket-submission.test.cjs` adds the result table to owned fixture cleanup; earlier missing-storage failure cases remain enforced.
- `tests/database/foundation.test.cjs`: eight-migration history and seeded 2/3/4/5/6/7 baseline upgrades. Existing queued jobs and active seventh-migration leases/attempts are retained; the new result store starts empty. No result is manufactured for old work.
- `scripts/consumer-smoke.mjs`: after real HTTP -> relay -> Kafka -> consumer admission, a trusted operator completes one leased job. Authenticated GET checks the completed result and an actual stored failure for reader/requester/operator; another tenant receives 404. Logs exclude the answer as well as questions, payloads and credentials. This test seam remains outside application images/public routes.
- Focused README/map/roadmap/contracts/data-model/operations and ownership-status updates. No executor loop, successful answer with citations, replay, real-provider feature or release is added.

## Limits and next step

The public result shape intentionally covers only a zero-citation, zero-tool, simulated abstention. The worker/API cannot label these stored results as real or answered. Future cited answers need their actual tenant/version-bound corpus/citation storage and evidence validation; the current schema is not a substitute for those FKs. Internal worker credentials remain trusted module credentials, not tenant RLS.

There is no polling executor, heartbeat loop, monotonic attempt deadline or active provider in this patch. Those must wrap the already implemented claim/renew/retry/fail/complete boundaries without a network call inside SQL. Normal submissions still queue until a reviewed caller executes the job. No model quality, throughput, exactly-once external effects or release readiness is established.
