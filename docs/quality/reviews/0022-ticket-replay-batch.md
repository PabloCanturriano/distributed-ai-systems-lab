## Limits and next boundary

Replay is an explicitly requested new generation of a failed ticket, not automatic redelivery, a reset of an existing attempt or repair of quarantined delivery. The initial failed fixture uses a trusted test-only worker actor, not a real provider failure or a public fault route. The normal provider still returns a fixed simulated abstention, which is a completed result and cannot be replayed. Retrieval, cited answers, tools, real-model inference, quarantine inspection/repair, complete telemetry and release remain outside this batch.

Internal API/worker roles remain trusted module identities without RLS. The new pointer UPDATE grant is column-scoped, but a compromised API is not constrained to forward-only lifecycle changes by a database procedure. Audit FKs/uniqueness and runtime insert-only grants protect the recorded structure; privileged migration/operator identities remain trusted. Public generation-history/audit queries, retention policy, throughput and recovery-time guarantees are not implemented by this slice.

Expected generation is capped at 2147483646 to permit a PostgreSQL integer increment. Fresh operators are rechecked inside the transaction; this does not claim instantaneous revocation fencing against concurrent identity changes. Replay shares existing submission mutation budgets. A client timeout can follow a committed replay; retain the same explicit key and generation to retrieve its receipt. A receipt is historical evidence of acceptance, not a promise that its generation remains current or has completed.
