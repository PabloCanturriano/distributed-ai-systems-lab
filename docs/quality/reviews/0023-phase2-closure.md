## Proposed logical commits

1. **`feat: add bounded OpenTelemetry tracing and durable origins`**
   - New `packages/telemetry` workspace, exact dependency/lockfile wiring, shared build and Docker inputs/runtime copies. Official `@opentelemetry/api` 1.10.0 and SDK/resources 3.1.1 run on Node 24.22.3. [Official SDK documentation](https://github.com/open-telemetry/opentelemetry-js/blob/main/packages/sdk-trace/README.md) describes manual instrumentation; the [3.x migration guide](https://github.com/open-telemetry/opentelemetry-js/blob/main/doc/3.x/migration-guide.md) explains the package/API transition. CJS/strict TypeScript compatibility is actually checked, not inferred.
   - Explicit parent contexts, fixed stages/outcomes and allowlisted metadata. Supported canonical version-00 context is 55 bytes with nonzero IDs and flags 00/01. Invalid/unknown/oversized/duplicate contexts are discarded; no baggage/tracestate is captured. SDK spans have bounded attributes and no events/links. A synchronous, bounded local stream projection has no exporter queue, network call or export timer and contains sink failures.
   - Tenth migration adds nullable constrained `trace_parent` columns to outbox/jobs with insert-only metadata grants. Submission/replay and admission preserve valid origin context outside business payload/digest/hash; malformed metadata takes the untraced path. Duplicate requests/delivery retain the first origins. Execution claims and terminal failure notifications can reuse the durable job origin. Existing null-origin rows remain usable; metadata does not authorize work.
   - Real PostgreSQL origin/idempotency/grant tests and upgrades from seeded baselines 2 through 9 preserve data, credentials and live job/lease/attempt state. SDK/stream tests check safe metadata, independent roots, invalid context, sink errors and backed-up buffering.
2. **`feat: correlate HTTP and CLI requests with safe trace hints`** (depends on 1)
   - API manual submission/replay/read spans, bounded validated incoming context, `traceparent`/`X-Trace-Id` response headers and safe outcome metadata. Receipts, authentication, request IDs and authorization remain unchanged. No automatic HTTP/header/SQL/exception capture is installed.
   - CLI validates response context, forwards it only to subsequent fixed-local-endpoint requests in that invocation and provides current/accepted trace hints. It does not invent a viewer URL or guarantee that a retried historical receipt identifies the original trace. Ticket/generation remain stable lookup keys.
   - Real HTTP tests prove parent propagation without changing receipt shape or leaking private fixtures, and exporter exceptions cannot change successful acceptance. CLI cases cover malformed context tolerance and polling continuity.
3. **`feat: propagate trace context through Kafka and job execution`** (depends on 1–2)
   - Relay creates publication children and sends actual Kafka `traceparent` headers while preserving stored key/bytes/event identity. The consumer validates header metadata, creates an admission child and persists the origin with the job. Executor spans use that durable context across process restart; concurrent handlers retain their own span state.
   - Live worker entry points initialize/shut down their local SDK ports; protocol classes retain no-op defaults for isolated tests. Existing ownership, SQL/offset sequencing, budgets and shutdown behavior remain active. Trace outcomes describe stage observations, not an independent durable-state authority.
   - Protocol tests verify child context propagation and successful durable operations even when the sink throws. No native artifact pin, business message version or external provider changes are introduced.
4. **`test: enforce the complete phase two acceptance gate`** (depends on 1–3)
   - `scripts/tracing-smoke.mjs`: empty-volume real CLI/HTTP → relay → Kafka-header → consumer → restarted executor journey, exported parent-chain assertions and durable context inspection across worker restarts. It also exercises concurrent HTTP idempotency, conflicts, same-tenant cross-member reads, foreign isolation, malformed context and a deliberately discarded real accepted response body followed by completion/same-key recovery. Only ordinary HTTP submissions and scoped service lifecycle operations mutate state; database inspection is read-only.
   - `docs/quality/phase2-acceptance.json`: unchanged required HTTP-01..05, EVENT-01..03, DATA-01..04 and CLI-01..04, explicit initial SEC-01..03 coverage and trace-correlation evidence selectors. References resolve to actual test/script assertions and required gates.
   - `scripts/phase2-check.mjs`, root commands and ignored generated evidence: fixed 11-command full gate; invalid/missing criterion, missing/focused/skipped referenced evidence, nonzero child result or changed implementation sources fail the run. The final report records base revision, implementation source digest, dirty status, environment, durations and coverage without raw logs. It is a completed-run record, not a live status file or an attestation for changed code.
   - CI adds `test:tracing` to both x64 and ARM64 after the committed replay gate. No required gate is replaced or silently skipped and no raw artifacts are uploaded.
5. **`docs: close phase two with verified acceptance and trace guidance`** (depends on 1–4)

## Closure boundary

Phase 2 means one inspected, deterministic, tenant-scoped ticket workflow with foundational distributed guarantees. It does not mean real AI, a release, high availability or complete phase 3. The SDK projection is local structured log output, not OTLP/Collector/Jaeger/Prometheus. Full metric/backlog/drop counters, telemetry-loss observation, export/collector outage acceptance, quarantine inspection/repair and later recovery families remain outstanding. No empty dashboard or unsampled URL is offered as evidence.

The sink skips records above 2 KiB or when stdout already exceeds 32 KiB; one accepted record can add up to 2 KiB before the next check. This does not bound unrelated logs or Docker disk retention. Context/response IDs do not prove a span was retained. Stage outcomes cannot resolve an ambiguous database acknowledgement; read authoritative state and keep the original retry key. Internal runtime roles remain trusted modules without tenant RLS. No credential/message/result data is used as span attributes or trace authorization.
